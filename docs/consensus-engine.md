# Consensus Engine — мульти-стратегия на одной монете

**Статус:** спецификация (код не написан). Дата: 28 мая 2026.
**Решения пользователя (зафиксированы):**
- Размер позиции — **аддитивные доли** (каждая подтверждающая стратегия добавляет свою долю notional).
- Стоп объединённой позиции — **самый тугой из активных** контрибьюторов.
- Порядок работ — **сначала этот спек**, ревью, потом код.

---

## 1. Проблема и неустранимый инвариант

Сегодня учёт ведётся по ключу **(symbol, strategy_id)** — каждая стратегия это
отдельная строка в `decisions`. Но аккаунт на Bybit принудительно в
**One-Way mode + cross margin** (`switchToOneWayMode` + `setCrossMargin` в
`src/strategies/user-fanout.ts`), а One-Way держит **одну нетто-позицию на
символ**. Это физика биржи — разбивкой по таймфреймам не обходится.

Пока все 9 стратегий на разных монетах (BNB/BTC/BCH/ETH/XRP/TRX/TON/HBAR/UNI)
коллизии нет. Как только появится 2-я стратегия на той же монете —
два независимых ордера дерутся за единственный слот: SL перезаписывается,
встречный «вход» закрывает чужую позицию, БД рассинхронизируется с биржей
(подробный разбор — в истории обсуждения / git-blame этого файла).

**Инвариант, на котором строится решение:** на символе у пользователя
всегда РОВНО ОДНА биржевая позиция и РОВНО ОДИН биржевой стоп.

## 2. Базовая развязка: два слоя

| Слой | Ключ | Бьёт на биржу? | Назначение |
|------|------|----------------|------------|
| **shadow** (`user_id IS NULL`) | 1:1 на `strategy_id` | нет | Чистый трек-рекорд каждой стратегии для лендинга. **Не меняется.** |
| **user-execution** | нетто на `(user_id, symbol)` | да | Реальные ордера. Здесь и только здесь происходит неттинг. |

Лендинг-статистика берётся из shadow → остаётся честной и раздельной по
стратегиям. Неттинг живёт исключительно в исполнении на счёте юзера.

---

## 3. Модель данных: «лоты» поверх существующей `decisions`

Никакой новой таблицы позиций — переиспользуем `decisions`. Каждая
подтверждающая стратегия по-прежнему создаёт **свою user-строку** (это «лот»).
Нетто-позиция на символе = алгебраическая сумма активных лотов:

```
net_qty(user, symbol) = Σ  signed(lot)           по всем active-лотам
   где signed(lot) = +bybit_qty (long) | −bybit_qty (short)
```

**Ключевая механика — каждый webhook порождает ДЕЛЬТА-ордер**, который доводит
биржевой нетто до нового целевого `Σ signed(lot)`:

```
target_net = Σ signed(active lots)  (включая/исключая текущее событие)
delta      = target_net − current_exchange_net
→ market order на |delta|, side = sign(delta)
```

Каждое событие меняет ровно ОДИН лот, поэтому дельта-ордер однозначно
сопоставляется с этим лотом: его филл = `bybit_qty` и `bybit_avg_price`
этого лота. Пример:

```
старт: flat
A long 10 @100   → target +10, delta +10 → buy 10.  Лот A=+10@100. net +10
B short 4 @110   → target +6,  delta −4  → sell 4.   Лот B=−4@110.  net +6
A exit @105      → target −4,  delta −10 → sell 10.   Лот A закрыт.  net −4
B exit @108      → target  0,  delta +4  → buy 4.     Лот B закрыт.  flat
```

**Новые колонки `decisions`** (миграция, см. §10):
- `symbol_net_after REAL` — снимок нетто-позиции символа после применения
  лота (для отладки/реконсайла).
- `lot_role TEXT` — `'open' | 'reduce' | 'flip'` — что делала дельта (для
  диагностики; не критично для математики).

`bybit_qty` / `bybit_avg_price` / `side` лота трактуем как **долю-намерение**
этой стратегии, не как полный фактический ордер (ордер — это дельта).

## 4. Размер позиции — аддитивные доли

Каждая стратегия вносит свою «долю» notional (как и сегодня:
`notional = tier.marginPerTrade × strategy.maxSafeLeverage`, помноженное на
`sl_pct_override`-логику Prof, если есть). Несколько подтверждающих лонгов
складываются:

```
symbol_long_notional  = Σ notional(active long lots)
symbol_short_notional = Σ notional(active short lots)
symbol_net_notional   = |long − short|
```

**Потолки (inventory caps) — обязательны, чтобы «складывание» не разнесло риск:**
- `MAX_SYMBOL_NET_NOTIONAL` — потолок нетто-экспозиции на ОДИН символ
  (производная от tier margin pool; напр. ≤ 40% пула).
- `MAX_LOTS_PER_SYMBOL` — макс. число одновременных лотов на символ (напр. 4).
- Кросс-ликвидационный нетто-чек (`|Σlong − Σshort| / equity ≤ 0.70/maxSlPct`)
  — уже есть в `user-fanout.ts`, переносится на уровень символа+портфеля.

Если новый лот пробивает потолок → лот **не открывается**, лог + (для не-Prof)
тихий skip, для Prof — warn-only (как сейчас). `maxConcurrentPositions` тарифа
**меняет смысл**: теперь это число **символов** с открытым нетто, не число
строк (см. §9 «Изменения в существующем коде»).

## 5. Стоп — самый тугой из активных

У биржевой позиции один SL. Берём **ближайший к цене стоп среди активных
лотов нужного направления**:

```
если net long:  position_SL = max( sl_price каждого active long-лота )   // самый высокий = самый тугой для лонга
если net short: position_SL = min( sl_price каждого active short-лота )  // самый низкий  = самый тугой для шорта
```

Пересчитывается **на каждое изменение книги** (вход/выход любого лота):
- после дельта-ордера вызываем `setPositionSL(creds, symbol, newTightestSL)`
  + `verifyOrAttachSL` (переиспользуем существующий код — атомарность и
  ретраи сохраняются, биржевой стоп НЕ теряем).
- стоп всегда едет в сторону ужесточения или ослабления в зависимости от
  того, какие лоты остались. **Важно:** биржевой SL никогда не двигаем в
  сторону, которая мгновенно выбьет уже открытую позицию (тот же принцип,
  что и «не ужесточаем SL на живой позиции до мгновенного стопа»).

**Последствие «самого тугого»:** когда срабатывает биржевой SL — закрывается
ВЕСЬ нетто (биржа знает только одну позицию). Это значит, что тугой стоп
одной стратегии выносит и доли остальных. Это сознательный консервативный
выбор пользователя; компенсируется тем, что лоты обычно однонаправлены и
коррелированы. Атрибуция — см. §7.

## 6. Потоки

### 6.1 Entry (webhook стратегии X, сторона S)
1. Shadow-строка пишется как сейчас (1:1, без неттинга).
2. `fanOutEntry` → для каждого eligible юзера `executeUserEntry`:
   a. preflight: маржа, inventory caps (§4), trading-active, идемпотентность
      по `parent_decision_id`+`user_id` (как сейчас).
   b. **leverage символа** = `min(maxSafeLeverage активных лотов + новый)` —
      см. §9 (леверидж теперь символьный, не построчный). `setLeverage`;
      `110044` (леверидж нельзя менять с открытой позой) больше не должен
      возникать, т.к. мы сами держим консистентный символьный леверидж.
   c. вычислить `target_net`, `delta`; если `|delta|`≈0 (лот не меняет
      направление сверх существующего, напр. дубль) → пропустить ордер,
      но лот всё равно зафиксировать в книге.
   d. `placeMarketOrder(side=sign(delta), qty=|delta|)` — **без** `stopLoss`
      в теле (стоп ставим отдельно символьным после, см. e).
   e. пересчитать `position_SL` (§5) → `setPositionSL` + `verifyOrAttachSL`.
      Если SL не встаёт после ретраев → закрыть весь нетто
      (`emergencyCloseUnprotected`-аналог на уровне символа) + критический
      алерт. Безопасность > сигнал.
   f. записать лот (`insertDecision` с `user_id`, `parent_decision_id`,
      `strategy_id`, `bybit_qty`=доля, `bybit_avg_price`=цена входа лота,
      `symbol_net_after`, `lot_role`).

### 6.2 Exit (webhook стратегии X)
1. Найти активный лот X на (user, symbol).
2. `target_net` пересчитать без лота X → `delta` → `placeMarketOrder`
   (reduceOnly, если delta уменьшает |нетто|; обычный market при флипе).
3. Пересчитать `position_SL` по оставшимся лотам → `setPositionSL`.
4. Закрыть лот X (`closeUserDecision`) с `force_reason='strategy_exit'`,
   `close_price` = филл дельты (или mark, см. §7).

### 6.3 Встречные сигналы (long + short)
Складываются в нетто алгебраически (пример в §3). Никакого спец-кейса —
`reverse_signal`-логика shadow остаётся только для shadow; на user-уровне
всё выражается через дельты.

### 6.4 Срабатывание биржевого SL
`tpsl-monitor` reconcile видит, что биржевой нетто закрылся (size=0).
Закрываем **все** активные лоты символа этого юзера с
`force_close_reason='sl_hit'`, `close_price` = SL-цена (или fetch-fills),
PnL атрибутируем по долям (§7).

## 7. Атрибуция PnL (честно про приближение)

**Источник правды о реальных деньгах юзера** — фактический реализованный PnL
нетто-позиции (из Bybit fills). **Per-strategy разбивка — индикативная**:

```
pnl(lot) = signed_qty(lot) × (exit_price(lot) − entry_price(lot)) − комиссии_доли
```

- `entry_price(lot)` — `bybit_avg_price` лота (филл его дельты).
- `exit_price(lot)` — филл дельты при закрытии лота, либо mark/SL-цена для
  массового SL-закрытия.
- Σ pnl(lot) ≈ реализованный PnL нетто (расхождение = остаточный слиппедж
  между дельтами). Расхождение логируем; если > порога — алерт-реконсайл.

Для лендинга используем shadow (1:1) — там атрибуция точная по построению.
В кабинете юзера показываем: портфельный реальный PnL (правда) + индикативную
разбивку по стратегиям (приближение, с дисклеймером в tooltip).

## 8. Reconcile (tpsl-monitor)

Сейчас reconcile сопоставляет одну строку ↔ одну позицию. Новое:
- На (user, symbol) берём **все активные лоты**, считаем ожидаемый
  `Σ signed = expected_net`.
- `fetchPosition(symbol)` → `actual_net`.
- `expected_net == actual_net` (в пределах qtyStep) → ок.
- `actual_net == 0`, но лоты активны → биржевой SL/ручное закрытие →
  закрыть все лоты `sl_hit` (§6.4).
- `|expected − actual|` дрейфует → **drift-алерт оператору** + НЕ авто-чиним
  вслепую (риск удвоить ордер). Оператор разбирает руками. Дрейф — главный
  риск-сигнал этой архитектуры.

## 10. Миграции

```sql
-- 0XX_consensus_lots.sql
ALTER TABLE decisions ADD COLUMN symbol_net_after REAL;
ALTER TABLE decisions ADD COLUMN lot_role TEXT;   -- 'open' | 'reduce' | 'flip'
-- индекс для быстрого расчёта нетто по активным лотам символа
CREATE INDEX idx_decisions_user_symbol_active
  ON decisions(user_id, symbol, status)
  WHERE user_id IS NOT NULL;
```

(`style` для стратегий — в TS-конфиге, не в БД.)

## 11. Стилевые пакеты (продуктовый слой, поверх движка)

Тегируем стратегии `style: 'scalp' (5m) | 'intraday' (15m–1h) | 'swing' (4h+)`.
Даёт понятные пакеты в тарифах и однородные по горизонту голоса внутри стиля
(их логичнее агрегировать). Это **дополнение**, не замена движка — без
Consensus Engine пакеты коллизию не решают (на 5m одной монеты тоже бывает 3+
стратегии). Делаем после ядра.

## 12. Фазы реализации

- **Phase 1 — Книга лотов + неттинг (ядро).** decisions-методы, дельта-логика
  в fanout, символьный SL/леверидж, caps. Тест на testnet: 3 лонга + встречный
  шорт на одной монете → ровно одна биржевая позиция, корректный нетто и SL.
- **Phase 2 — Reconcile + drift.** tpsl-monitor нетто→лоты, массовый sl_hit,
  drift-алерты. Тест: эмулировать биржевой SL и ручное закрытие.
- **Phase 3 — Атрибуция PnL + UI.** долевой PnL, дисклеймеры, пересчёт
  маркетинговых чисел тарифов.
- **Phase 4 — Стилевые пакеты.** `style`-тег, упаковка тарифов, лендинг.

Каждая фаза: typecheck + lint + tests + shadow-валидация перед mainnet.

## 13. Открытые вопросы (решить до Phase 1)

1. **Символьный леверидж при разных `maxSafeLeverage`.** Берём `min` (самый
   консервативный). Подтвердить, что это не режет notional сильнее, чем
   ожидается (min-леверидж × Σ долей).
2. **Потолок `MAX_SYMBOL_NET_NOTIONAL`** — конкретный % от tier margin pool
   (предложение: 40%). Влияет на worst-day SL — пересчитать таблицу тарифов.
3. **Reduce vs flip приоритет при выходе одной из встречных стратегий** —
   уточнить поведение, когда выход лота переворачивает нетто (редко, но надо
   детерминированно).
4. **Порог drift-алерта** (в qtyStep / %) для §8.
```
